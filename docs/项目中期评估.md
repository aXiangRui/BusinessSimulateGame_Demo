# 项目中期评估

> 评估日期：2026-07-06  
> 当前版本：重构后（GameEvent → GameWorld + GameSerializer + TimeOfDaySystem）  
> 评估范围：玩法设计、代码架构、代码风格、工程习惯

---

## 一、创新点

### 真正有意思的地方

**甜品合成系统** — 基类蛋糕（蛋糕胚）+ 三种装饰材料 → 独一无二的产品。甜度/饱腹感/口感三个维度不只是数值，它们直接影响顾客的选择和偏好积累。这个系统的深度在同类小游戏中很少见。

**顾客偏好成长** — 每个顾客有隐藏的好感度，吃了喜欢的甜品会涨偏好值，偏好值又反过来解锁新内容（新顾客、新甜品、新材料）。这是一个自循环的进度系统，比单纯的"攒钱→买升级"更有黏性。

**排队付款机制** — 从 `payQueue` 到服务员状态机（waiting→paying→handing），收银员只有一个在岗的约束，甜品从小蛋糕生成到服务员送到面包柜——这是一条完整的物理流水线，不是简单的数值加减。

**昼夜循环** — 不只是换个背景色，而是实实在在地影响游戏节奏：白天正常营业，晚上没顾客就加速跳过，午夜结算扣钱补货。时间管理与经营模拟的结合做得很自然。

### 可以深挖的方向

甜品合成的"组合爆炸"还没完全发挥——三个维度的食材搭配如果能触发隐藏配方或 combo 加成，会让玩家更有动力实验。顾客偏好值已经是一个很好的数据基础，后面做"老顾客回忆录"之类的叙事玩法会很有感染力。

## 二、代码水平

### 亮点

**场景系统** — `RUI_Scene` 基类 + `RUI_SceneManager` 调度，onEnter/onUpdate/onRender/onInput/onExit 生命周期清晰。比很多新手一个 main 循环撸到底强太多了。

**ResourceManager 单例** — 用 `WIN32_FIND_DATAA` 递归扫描 resources 目录，自动加载所有贴图/音频/音乐，按文件名索引。实现方式虽然偏 Windows 专用，但思路是对的，避免了到处手动 Load 的噩梦。

**存档系统** — 自定义 `.rui` 格式，多个文件分模块存储（Time / Total / Cabinet / Employee / Customers…），比一个巨大 JSON 或者二进制 blob 更容易调试和维护。

### 需要提升的

**重构前是典型的"能跑就行"代码**。GameEvent 732 行塞在一个头文件里，既有 150 行的存档读写，又有 200 行的游戏更新逻辑。GameScene 50 个 public 成员散落一地。这不是能力不够，而是快速迭代时的惯性——功能跑通就不回头了。

**缺少防御性编程**。文件读写没有错误恢复（Load 失败直接崩），`SDL_GetError()` 几乎没用过，空指针检查看心情。对一个小游戏来说不是致命问题，但如果想把这个项目放到简历上，这部分会很扣分。

**const 几乎没有**。`Customer::GetCustomerName()` 不标记 const，导致后面所有使用 `const Customer&` 的地方全部炸裂——重构时遇到的连锁反应就是最好的证明。

**内存管理偏原始**。SDL_Texture 混用 ResourceManager 共享和本地 `SDL_CreateTextureFromSurface`，有些地方 Create 了忘记 Destroy，字体也是每个类各自 `TTF_OpenFont` 而不是统一管理。

## 三、代码风格

### 命名

命名整体**可读性不错**——`CustomerManager`、`InitCabinet`、`DeleteCustomer` 都能望文生义。但一致性确实不太行：

| 类 | 命名风格 |
|----|---------|
| RUI_GameScene | RUI_ 前缀 |
| GameEvent | 无前缀 |
| CabinetFrame | 无前缀 |
| SummaryFrame | 无前缀 |
| MaterialManager | 无前缀 |
| RUI_Icon | RUI_ 前缀 |

有的带 RUI_，有的不带，说明是陆陆续续加上去的，没有一开始就定好规范。

中英文混用也很典型——`WhetherReadingProduct`、`WhetherRenderCustomerFrame`、"钱够不够"和"TotalMoney"并存。对于个人项目无所谓，但是如果以后想开源或者给其他人看，建议统一全英文命名。

### 注释

注释量刚好——不是那种每个变量都写一句废话的风格，但关键位置有中文说明（`//防溢出，不过基本上也没人能招待这么多吧...`，`//差点找不到顾客类刷新了哈哈哈哈`）。这些带情绪的注释说明这个项目是真心在做的，不是应付作业。

## 五、一句话总结

**这是一个有想法、有设计、但工程基本功还在成长的独立游戏项目。**

你主动提出重构、思考架构问题、写设计文档——这些习惯比写出"完美代码"更值钱。保持这个节奏，随着项目继续迭代，代码质量会自然跟上你的设计能力。
